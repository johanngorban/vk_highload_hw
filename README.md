# 1. Тема и целевая аудитория

## Тема
Облачная платформа умного дома, к которой пользователь подключает "умные" бытовые устройства: чайник, розетки, принтеры и др. умную технику. Управление осуществляется через мобильное приложение: пользователь управляет, видит состояние, настраивает сценарии автоматизации (как Умный дом от Яндекса) и получает уведомление (например, о задымлении).

Реальные аналоги: Умный дом от Яндекса и Xiaomi Home.

## Функционал MVP

1. Регистрация и авторизация. Пользователь создаёт аккаунт по номеру телефона или email и входит в приложение. Сессия сохраняется на смартфоне и продлевается без повторного ввода пароля.
2. Подключение устройства и управление домом. Пользователь добавляет новое устройство в дом, распределяет устройства по комнатам и приглашает членов семьи с разными правами доступа.
3. Управление устройством. Пользователь отправляет команду (включить, выключить, изменить яркость или температуру) и получает обратную связь.
4. Состояние устройств в реальном времени.В приложении видно текущее состояние всех устройств дома и статус в сети.
5. Сценарии и автоматизации. Действия запускаются по расписанию или по событию от устройства, например "Датчик открытия двери сработал после 23:00, включить свет в прихожей".
5. Уведомления о событиях. Пуш-уведомления о срабатывании датчиков протечки, дыма, движения и открытия, а также о переходе устройства в офлайн.

# 3. Глобальная балансировка нагрузки

## Функциональное разбиение по доменам

| Домен | Что входит | Размещение |
|---|---|---|
| Устройства | MQTT-брокеры, прием телеметрии, доставка команд | В каждом регионе |
| Приложение | API, состояние дома, история, WebSocket | В каждом регионе |
| Сценарии | Движок автоматизаций | В каждом регионе, рядом с брокерами |
| Телеметрия | Хранение рядов, агрегация | В своем регионе, без вывоза наружу |
| Аккаунты | Регистрация, авторизация, реестр пользователей и привязок устройств | Глобальный: мастер плюс реплики в регионах |
| Уведомления | Отправка push в APNs и FCM | Из любого региона |

Первые четыре домена привязаны к региону: они работают с устройствами и их данными. Глобальный только домен аккаунтов, потому что пользователь должен входить в аккаунт из любой точки.

## Расположение дата-центров

Регионы выбраны по структуре аудитории: Россия и СНГ - основные регионы, страны Латинской Америки - второй по приоритету регион. Во всех странах ставить сервера невыгодно: нет достаточного количества пользователей; при этом в некоторых странах законодательство обязывает хранить персональные данные на территории государства (Россия).

| Регион | Доля аудитории | ДЦ |
|---|---|---|
| Россия | 55% | Подмосковье (Зеленоград), Новосибирск |
| Казахстан | 25% | Алматы (буферизируется на РФ) |
| Латинская Америка | 20% | Аргентина (не менее 2-х) |

По два ДЦ на регион, резервирование N+1: при отказе одного ДЦ второй принимает весь регион. Отказ региона целиком переводит трафик на соседний, с ростом задержки.

Выбор Аргентины обоснован стоимостью киловатт-часа, а также тем, что там проще найти специалистов (рядом Бразилия, а киловатт-часа делает трансфер выгоднее).

Влияние на продуктовые метрики:
- Задержка команды. Цель — реакция устройства до 300 мс от нажатия, поэтому должен отвечать ближайший ДЦ
- Обнаружение офлайна. Брокер и устройство в одном регионе, иначе межконтинентальные обрывы дают ложные срабатывания.
- Хранение данных. Телеметрия остается в регионе сбора

## Схема DNS-балансировки

Приложение: одно имя api.smarthome.ru, GeoDNS отдает адрес ближайшего региона по адресу резолвера, TTL 60 секунд. Внутри региона отдаются адреса обоих ДЦ с весами.

Устройства: регион зашивается при первичной привязке устройства, дальше оно ходит по имени своего региона, например ru.mqtt.smarthome.ru, kz.mqtt.smarthome.ru, la.mqtt.smarthome.ru. Это нужно, чтобы устройство не переезжало в другой регион при смене DNS-резолвера у провайдера, и чтобы данные российских пользователей не уходили за границу.

DNS-серверы подняты по Anycast: один и тот же адрес объявляется из всех ДЦ, запрос приходит в ближайший.

Сам трафик через Anycast не идет. MQTT-соединение живет часами, а смена маршрута BGP рвет TCP-сессию и вызывает лавину переподключений. По той же причине Anycast не используется для WebSocket.

## Регулировка трафика между ДЦ

| Механизм | Для чего | Скорость |
|---|---|---|
| Веса в GeoDNS | Плавный перевод доли приложения между ДЦ и регионами | Минуты, по TTL |
| Server Reference в MQTT | Брокер при отключении сообщает устройству адрес другого ДЦ | Секунды |
| Ограничение темпа перевода | Не более 1% соединений региона в минуту | Защита от лавины переподключений |
| Снятие анонса префикса | Вывод ДЦ из эксплуатации целиком | Секунды |

Перевод 135 млн соединений мгновенно невозможен из-за огромного количества TLS-соединений (нагрузка большая).  Поэтому перевод растянут по времени, а при аварии второй ДЦ региона принимает устройства волнами по мере их попыток переподключения.
